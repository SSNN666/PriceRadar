## 1. 凭证与探针

- 凭证：`PDD_CLIENT_ID` / `PDD_CLIENT_SECRET` / `PDD_PID`（`.env`）

## 3. `pdd.ddk.goods.detail` 实测

### 3.1 结论：**不建议接入**

`search` 返回 **54** 字段，`detail` 返回 **55** 字段，净增仅三项：

- `mall_img_url`（店铺 logo）
- `goods_gallery_urls`（轮播图）
- `video_urls`（样本为空）、`material_list`

→ 除轮播图/店铺 logo 外**无增量价值**，不必为"补字段"接入。

### 3.2 商品评价分 / 评价数量：文档声明有，实测无 ❌

文档明确写 `pdd.ddk.goods.detail` 返回"商品评价分、商品评价数量"，但实测**响应中不存在** `goods_eval_score` / `goods_eval_count` 等字段（逐字段核对确认）。

这是本项目第四次"文档说有、实测没有"（前三次：`goods.query` 403、`promotiongoodsinfo` 403、`goods.activity.query` 只返历史存档）。

### 3.3 ⚠️ 修正：店铺 DSR **确实返回**（但为文字档位）

**初版记录写成"店铺 dsr 无此字段"，这是错的。** 实际返回在三个**容易被误认为通用文本字段**的键里：

| 字段 | 含义 | 实测值 |
|---|---|---|
| `desc_txt` | 店铺描述分 | `"高"` |
| `lgst_txt` | 店铺物流分 | `"高"` |
| `serv_txt` | 店铺服务分 | `"高"` |

即：**DSR 以档位文字（高/中/低）返回，不是数值**。可作为店铺质量的分档信号使用。

> 教训：字段名 `desc_txt`/`serv_txt` 长得像普通描述文本，光看名字判断"没有 DSR"会漏掉。

### 3.4 店铺名称：字段在但为空

`mall_name` = `""`（`search` 与 `detail` 均为空）。但 **`mall_id` 可用**（店铺 id），可用于"同店多商品"分析。

`merchant_type` 两个接口都返回。

## 4. `pdd.ddk.goods.search` 能力边界（实测 + 证伪）

### 4.1 ✅ 生效的能力

| 能力 | 实测证据 |
|---|---|
| 关键词搜索 | 正常 |
| `merchant_type` 筛选 | 传 `3` → 返回 9 条，类型集合 = `[3]` |
| `merchant_type_list` 筛选 | 传 `[3,4]` → 返回 10 条，类型集合 = `[3]` ✅ |
| `sort_type` 价格排序 | `3`(价格升序) 结果与综合排序明显不同 ✅ |
| `sort_type` 销量排序 | `5`(销量升序) 结果与综合排序明显不同 ✅ |
| `keyword` 传商品链接 | **支持**，但见 §4.3 |

### 4.2 ❌ `range_list` 被接受但完全忽略（证伪测试）

文档给出 20 个可筛选维度（含**商品分**、**店铺描述分/物流分/服务分**、销量、价格等），但实测**全部不生效**。证伪方式——传**不可能满足**的区间，若仍返回结果即证明被忽略：

| 筛选 | 返回条数 |
|---|---|
| 无筛选（基准） | 8 |
| 商品分 `0~0.01`（不可能满足） | **8** |
| 店铺描述分 `0~0.01`（不可能满足） | **9** |
| 拼团价 `0~1` 分（一分钱耳机） | **8** |
| 销量 `0~1` | **9** |

**结论：`range_list` 参数不报错但被忽略**，与 `goods.activity.query` 的 `type`/`actStatus` 被忽略是同一现象。

> 教训：**"没报错"不等于"生效"**。判定筛选是否生效必须用"不可能满足的区间"做证伪，不能凭两次结果条数不同下结论（结果池本身在抖动，见 §4.4）。

### 4.3 链接查询：支持，但必须是**原始链接**

`keyword` 可传"拼多多链接（即拼多多app商详的链接）、进宝长链/短链"。实测：

```python
# ❌ 手工构造的链接 —— 被拒
c.call('pdd.ddk.goods.search', keyword='https://mobile.yangkeduo.com/goods.html?goods_id=877154015469', ...)
# → PddApiError: 该查询不是来自终端用户的原始链接，请使用原始链接进行查询
#   （参考 https://jinbao.pinduoduo.com/qa-system?questionId=388）
```

**能力存在，但必须是用户从 App 真实分享出来的原始链接**（携带平台下发的标识参数），手工拼 `goods.html?goods_id=xxx` 不算。

> **产品含义**：若验证通过，则"用户在拼多多 App 图搜 → 复制商品链接 → 我们直接查"这条路可行，**无需图搜 API、无需爬虫**。待用真实分享链接验证（见 §9）。

### 4.4 ⚠️ 结果集不可复现

**同一查询连续执行两次，返回的商品集合/顺序不同。** 传 `use_customized=false` 亦然（三次结果仍不一致）。

原因：商品池实时变化（上下架、库存、活动）+ 可能的推荐扰动。

> **对快照采集的影响**：按关键词采集的快照，**商品集会逐日漂移**——某商品今天采到、明天不在结果里，价格序列就会断。这解释了快照库里大量商品"只观测到 1-2 天"。若要跟踪特定商品的价格历史，应改用**按商品稳定标识采集**（如 goods_sign / mall_id+goods_id），而非按关键词反复搜。

## 5. `pdd.ddk.goods.recommend.get`：平台原生"相似商品推荐" ✅

### 5.1 频道语义（实测）

| `channel_type` | 含义 | 与参考商品的相关性 |
|---|---|---|
| **3** | **相似商品推荐** | ✅ **唯一能找相似商品的频道**（需传 `goods_sign_list`） |
| 1 | 今日销量榜 | ❌ **全局榜单**，与参考商品无关（实测含"裙" 0%） |
| 5 | 实时热销榜（默认值） | ❌ 全局榜单，无关（实测 0%） |
| 4 | 猜你喜欢 | 需 `pid` / `custom_parameters`（备案） |

> ⚠️ 关键：`channel_type` **默认值是 5**（实时热销榜）——即不传该参数时返回的是全局热销榜，**与查询商品毫无关系**。要"找相似"必须显式传 `3`。

调用示例：

```python
c.call('pdd.ddk.goods.recommend.get', channel_type=3,
       goods_sign_list=json.dumps([goods_sign]),  # 仅取数组第一位
       limit=20, offset=0, pid=c.pid)
# → goods_basic_detail_response.list
```

### 5.2 精度实测：**随品类差异极大**

以返回结果中是否含品类关键词做粗测（样本量为单次 15-20 条，仅供量级参考）：

| 参考商品 | 返回条数 | 相关条数 | 相关度 |
|---|---|---|---|
| 保温杯 | 20 | 20 | **100%** |
| 降噪耳机 | 15 | 7 | **~47%** |
| 连衣裙 | 15 | 5 | **~33%** |

**规律：功能明确的标品/日用品精度高；款式驱动的服饰类精度低。**

这与本项目同款匹配的核心困境一致——**标品好办，非标品难**。不要指望用该接口替代同款判定，它只能作为**候选来源**。

### 5.3 额外的信号字段（仅此接口提供）

| 字段 | 含义 |
|---|---|
| `realtime_sales_tip` | **商品近 1 小时实时销量**（仅实时热销榜提供） |
| `goods_rate` | 商品等级 |
| `qr_code_image_url` | 二维码主图 |
| `share_desc` | 分享描述 |
| `market_fee` | 市场服务费 |

> ⚠️ 数据形状不一致：本接口 `merchant_type` 为 **STRING**，`cat_id` / `opt_id` 也是 STRING；而 `goods.search` 中 `merchant_type` 为 **INTEGER**、`cat_id` 为 LONG。映射层需做类型兼容，否则会出现"同一字段两种类型"的解析坑。

**`merchant_type` 分布**：

| 值 | 类型 | 占比 |
|---|---|---|
| 3 | 旗舰店 | **64%** |
| 1 | 个人 | 14% |
| 4 | 专卖店 | 9% |

**⚠️ 两个信号相互独立**：评分档位为"低"的 7 个商品中，**5 个是旗舰店**、2 个是个人店。

→ **旗舰店不等于评分高**。再次印证 §6.3 的诚实边界：资质与质量是两回事，不可互相替代。

### 6.3 产品含义

能拿到的质量信号恰好都是**平台背书型**——评论可以刷，但"正品险""假一赔十"是平台要担责的承诺，"旗舰店"是平台认证资质。

> 拼多多侧的质量叙事应为「**看平台敢不敢承诺**」，而非「比用户评价」。

⚠️ 诚实边界（有实测支撑，见 §6.2）：`merchant_type` 是**资质**不是**质量**；个人店也可能卖好货。筛选是**降低风险**，不是**保证质量**。

## 8. 优惠类字段核对（2026-10-07 已闭环）✅

扫描 187 个商品（10 个关键词），逐项确认「是否计入到手价」：

| 字段 | 实测出现率 | 结论 |
|---|---|---|
| `clt_cpn_*`（**店铺收藏券**） | **5%** | ✅ **已接入**。面额 300/500 分（3/5 元），门槛=面额（等效无条件立减），有剩余量可领，**与商品券互斥出现**（0 个并存 → 无需叠加逻辑）。时间戳为**秒级**（京东是毫秒，勿混用） |
| `extra_coupon_amount` | 2%（3/3 与 `coupon_discount` **数值完全相同**） | ❌ **不接入**。是同一张券的**重复字段**，相加会双倍计优惠、到手价虚低 |
| `cash_gift_amount`（全局礼金） | **0%** | 不接入（实测未出现） |
| `subsidy_amount`（渠道补贴） | **0%** | 不接入——且语义上是给**推广渠道**的补贴，非消费者优惠 |
| `mall_coupon_*`（店铺折扣券） | **0%** | 未接入：属比率券，引擎只支持面额券（保留待办） |

### 8.1 口径决策（已写入 PRD §6.1）

计入到手价的券必须满足「**无资格门槛、任何人可领**」：

- ✅ **店铺收藏券计入**：需"收藏店铺"这个**操作**，但无**资格**门槛、人人可领。不计入会让展示价高于用户实际能拿到的价。代价是条件必须写进标签——明细实测显示为 `店铺收藏券（需收藏店铺）满3减3`
- ❌ 个性化券（PLUS/新客/账号专属）不计入 → 走 §5.6 用户补录
- ❌ 渠道专属补贴不计入 → 那是给推广渠道的

**修正效果**（真实数据端到端验证）：

```
标价 ￥7.66  ->  到手 ￥4.66   明细: 7.66 - 店铺收藏券（需收藏店铺） 满3减3 3 = 4.66
```

### 8.2 教训：**"字段没映射"和"字段该不该映射"是两件事**

`extra_coupon_amount` 字面上像"另一张额外优惠券"，实际是 `coupon_discount` 的重复字段。若按"把没用的字段都接上"的思路做，会得到一个**看似更优惠、实则虚低**的到手价——比漏算更糟（漏算只是价偏高，用户仍安全；多算会误导用户）。

故本项目的核对顺序应是：**先验语义（是否重复/是否互斥），再定口径（该不该计入），最后才改代码。**

## 10. ⚠️ 账号限流（2026-10-07 实测踩到）

**报错原文**：

```
当前duoId因大量调取商品接口但出单较少被限制使用
```

**触发经过**：本日做字段探测与验证时高频调用 `goods.search`（数十次），随后该账号被限制，`search_goods` 全部失败；持续 **20 分钟以上未自动恢复**。

### 10.1 为什么这是结构性风险

限流判据是「**调用量 vs 出单量**」。而本项目的账号按定义**永远不会出单**——用户通过我们的链接下单才会产生订单，种子期（自己 + 同学）出单量必然趋近于零。

> **也就是说：我们的账号天然处在"调得多、出得少"的状态**，调用量一上来就可能被限。

### 10.2 影响面

| 受影响 | 程度 |
|---|---|
| **每日快照采集** | ⚠️ 直接依赖 `goods.search`，被限流则当天采集失败（而快照过期不补） |
| Web/CLI 查询 | ⚠️ 拼多多是主数据源，被限则查询不可用 |
| 京东侧 | ✅ 不受影响（本次实测 JD 在同期的 80 次刷新调用后仍正常） |

### 10.3 应对

- **控量**：快照按关注清单每天一次（5 个关键词 ≈ 5 次调用，量很小，正常不应触发）；避免调试期高频轰炸
- **京东走缓存**（`jobs/jd_pool.py`）：把京东侧 API 调用从"每次查询"降到"每天一次"
- **不重试限流**：限流属业务错误（`PddApiError`），`sources/retry.py` 判定为不可重试——重试只会加重限制，判断正确
- **待验证**：官方是否提供申诉/提额通道；以及限制的恢复时间规律（本次 >20 分钟）

### 10.4 与京东限流的区分（避免误判）

京东联盟**也有**"调用量 vs 出单量"类限制，但报错文本不同。实测中"duoId"字样即**拼多多**（多多客 ID）；京东用 appKey/unionId。本次限流事件中，京东侧在同期 80 次刷新调用后**完全正常**。

### 5.4 已落地（2026-10-07）

`channel_type=3` 已接入产品，成为**「以商品为锚点找相似」**能力：

- 代码：`PddClient.recommend_similar(goods_sign, limit)`
- 接口：`GET /api/similar?goods_sign=...`（前端每条报价上的「找相似」按钮）
- 实测：锚点「富光 316L 保温杯 ￥45.8」→ 18 条相似商品，其中**同品牌 ￥41.5**（便宜 4.3 元）、最低 ￥33.8；
  每条都附店铺资质与质量评估

**这是"图搜图做不了"的合规替代**：用户看到想买的东西 → 在拼多多搜到它 → 以它为锚点让平台找相似的 → 挑最便宜的。
不碰图搜 API、不碰爬虫。

## 11. 商品链接解析（2026-10-07 验证通过）✅

### 11.1 结论：`goods.search` 的 `keyword` 可直接吃用户分享的链接

```python
c.call('pdd.ddk.goods.search', keyword='<用户分享的链接>', page=1, page_size=10, sort_type=0, pid=PID)
# → 精确反查到那件商品（返回 1 条，goods_id 与链接一致）
```

实测样本（用户从 App 分享）：

```
https://mobile.yangkeduo.com/goods.html?goods_id=726516013895&uin=AQ6OH5TPS2RZ7GMOS6H2RBQTMA_GEXDA
→ 【羽博】适用AirPods5保护套锁扣弹盖Pro3/2  ￥25.7
```

### 11.2 ⚠️ 关键约束：`uin` 参数是必需的，**绝不清洗 URL**

| 输入 | 结果 |
|---|---|
| 完整链接（含 `uin`） | ✅ **精确命中** |
| **去掉 `uin`** 的同一链接 | ❌ *"该查询不是来自终端用户的原始链接"* |
| 只给 `goods_id` | ❌ 同上 |

`uin` 是分享者的用户标识，平台以此证明"这是终端用户真实分享"。**任何"规范化 URL /
剥掉 tracking 参数"的习惯做法都会正好把它剥掉，然后被拒**——这是实现时最容易犯的错。
故 `sources/links.py` 只做识别、原样返回，不解析也不重建。

### 11.3 附带能力：转链可用（此前认知有误）

`pdd.ddk.goods.promotion.url.generate` **可用**，参数名是 **`p_id`**（不是 `pid`，传错报"请求参数不能为空：p_id"）。
返回 6 个 URL 字段：`mobile_url` / `mobile_short_url` / `url` / `short_url` / `we_app_web_view_url` /
`we_app_web_view_short_url`。

且**生成的进宝长链/短链可直接当 `keyword` 反查**（实测均精确命中）——形成
`goods_sign → 链接 → 商品` 的双向通路。

> 注：此前记录的"转链不可用"指的是**京东侧**（`promotion.bysubunionid` 403）；拼多多侧一直可用，只是没接。

### 11.4 链接查询的自动扩展（实现决策）

按链接搜索**只返回那一件商品**（没有比价对象）。而用户粘链接的意图恰恰是"这个值不值"，
所以 `search_pdd_goods` 在识别到链接时会**自动调用相似推荐扩展候选池**（`channel_type=3`）。

实测该样本：候选池 1 → 15 条。但**14 条相似商品被"品牌不同"排除**（源是【羽博】，
相似推荐给的是别的品牌）——对 AirPods 保护套而言，不同品牌确实是不同商品，
**匹配器的判断是对的**。故链接查询的典型结果是「1 个报价 + 诚实说明」，
这仍是对"值不值"的有效回答，且比"只有关键词搜不到"强。

## 12. ⚠️ 类目空洞：部分品类没有进宝商品（2026-10-08 实测）

### 12.1 现象

`goods.search` 对某些关键词返回 **`total_count=0` 且 `goods_list` 为空**——**不报错，就是没货**。

实测样本（同日、同一凭证、交替调用以排除限流）：

| 返回空 ❌ | 正常返回 ✅ |
|---|---|
| 手机、平板、显示器、显示屏、电视 | 保温杯(9)、降噪耳机(8)、笔记本(10) |
| 键盘、鼠标 | 手表(3)、音箱(7)、充电宝(8)、数据线(6)、路由器(6)、洗发水(10) |

**规律：整机（手机/平板/显示器/电视）与电脑外设（键盘/鼠标）为空；日用品、配件、音频类有货。**

### 12.2 排除项

- ❌ **不是限流**：同一批测试中「保温杯」「降噪耳机」「笔记本」均正常返回，限流会全站失败（见 §10）
- ❌ **不是代码 bug**：直接调 API 即返回 `total_count=0`
- ✅ 是**平台侧"屏蔽的类目&关键词"**机制——`search` 的入参 `block_cat_packages` 第一项即「拼多多小程序屏蔽的类目&关键词」，说明书该机制确实存在

> 推测原因（未经证实）：这些品类是百亿补贴/官方定价的主力，或进宝佣金无吸引力，故无进宝商品。**不深究，按"没货就是没货"处理。**

### 12.3 产品处置

1. **报错文案必须说清原因**（已实施）：原文案「关键词 '显示器' 无检索结果」看起来像程序坏了。
   现改为说明「该品类没有进宝商品、不是故障」，并给出可行出路（换品类 / **粘贴商品链接**——链接反查已验证可用，见 §11）。
2. ⚠️ **不要建议"换同品类的说法"**：屏蔽的是**类目**，换成"小米显示器"同样为空。
3. **口径**：这是平台数据边界，与 §10 的账号限流是两回事，PRD §10 风险表可各记一条。

### 12.4 待评估

- 管线目前**必须有拼多多池作为源商品**，故拼多多无货即整条查询失败——即使京东侧有货。
  可考虑降级为「京东可独立成单」（以京东商品为源），但属设计变更，未启动。
- `pdd.goods.cats.get` / `pdd.goods.opt.get` 能否取到屏蔽类目清单，未探测。
