# PRD · 真价雷达（到手价决策 Agent）v0.1

> 项目代号：PriceRadar ｜ 文档状态：选型已定稿，待评审
> 日期：2026-10-04

## 1. 产品定位

**一句话**：用户粘贴商品链接或淘口令，Agent 计算各平台叠加优惠券、满减、返佣后的**真实到手价**，给出"在哪买、现在买还是等"的决策建议。

**不是**又一个标价比价工具。核心差异：

| 维度 | 慢慢买/购物党 | 平台 AI（千问/京言） | 开源比价项目 | **真价雷达** |
|---|---|---|---|---|
| 比的是什么 | 标价+券后价 | 生态内价格 | 标价 | **跨平台到手价**（券+满减+返佣叠加） |
| 跨平台 | 是 | 否/弱 | 是 | 是 |
| 数据来源 | 自建十年库（壁垒） | 平台内部 | 爬虫为主 | **官方联盟 API（合规）** |
| 买入时机 | 有（历史库） | 无 | 无 | 自采快照 + 时机建议 |
| Agent 化 | 否 | 有限 | 是 | LangGraph 多 Agent + MCP 化 |

**目标用户**：网购高频用户；首发种子人群为应届生/同学（大促决策场景集中，易获取反馈）。

## 2. 核心用户故事

1. 用户在淘宝看到一双鞋 ¥399，复制链接发给 Agent → 收到回复：京东叠券+返佣后到手 ¥331，拼多多 ¥345，淘宝 ¥368，**建议京东下单，附跳转链接**。
2. 用户问"这个价值得买吗" → Agent 展示自上线以来观测到的价格区间，判断当前到手价处于低位/中位/高位，给出"现在买/再等 7 天"建议。
3. 用户关注商品后降价 → 收到降价提醒推送。

## 3. 功能范围

### P0 · MVP（必须做完才能上线）
- 商品链接/淘口令解析（京东、拼多多、淘宝三平台）
- 同款商品跨平台识别（标题+规格 embedding 匹配 + 规则校验）
- **到手价引擎**：标价 − 店铺券 − 平台券 + 满减分摊 + 返佣，确定性规则计算（LLM 不参与算钱）
- 到手价对比卡片（平台/标价/券明细/到手价/推荐结论 + 溯源链接）
- 自然语言问答（预算澄清、品牌偏好追问）

### P1 · 上线后 4 周内
- 价格快照定时采集（append-only），历史曲线（诚实标注观测天数）
- 买入时机建议（分位数规则模型，非 LLM 编造）
- 降价提醒（关注商品 + 阈值推送）
- 报告可分享（图片/Web 链接）
- **识图找同款**：上传/粘贴商品图 → 图搜定位同款 → 直接进比价管线（技术方案见 5.5）

### P2 · 远期
- **MCP Server**：把解析/比价/到手价能力封装为 MCP 工具，Claude/Cursor 用户即用（国内空白）
- 浏览器插件（商品页侧边栏浮层）

### 明确不做（红线）
- ❌ 不获取用户平台账号 / 不做 Cookie 代爬 / 不自动下单
- ❌ 不做全站商品库，只服务用户查询过的商品（长尾商品按需采）
- ❌ 定位信息仅 P2 考虑（区域补贴价），MVP 不做

## 4. 系统核心流程

```
用户输入(链接/口令/自然语言)
  → 意图理解 Agent（要不要比价？缺什么信息？）
  → 商品解析 Agent（平台识别 → 联盟/转链 API 取商品详情+券+返佣）
  → 并行平台查询（其他两平台搜索同款 → 候选集）
  → 同款匹配（embedding 召回 + 规格规则校验，输出置信度）
  → 到手价引擎（确定性计算，逐项列公式）
  → 报告生成 Agent（结构化输出：对比卡片 + 建议 + 免责声明）
```

失败降级：同款匹配置信度低时，明确标注"未找到确切同款，以下为近似款"，不假装精确。

## 5. 技术架构

### 5.1 数据接入层（项目成败关键）
| 平台 | 通道 | 说明 |
|---|---|---|
| 京东 | 京东联盟 API（jd.union） | 个人可注册；商品详情、优惠券、返佣比例 |
| 拼多多 | 多多进宝 API（pdd.ddk） | 个人可申请；同上 |
| 淘宝 | 折淘客/大淘营等第三方转链 API | 淘宝联盟需媒体资质，个人走不通；第三方按调用量计费，MVP 期成本可控 |

### 5.2 Agent 层
- 编排：**LangGraph** 状态机（面试核心叙事点）
- 节点：意图理解 / 商品解析 / 并行查询 / 同款匹配 / 到手价引擎（纯函数工具）/ 报告生成
- LLM：DeepSeek-V3（意图理解、追问澄清、报告文案），结构化输出走 JSON Schema + 校验重试
- 同款匹配：bge-small-zh embedding 召回 + 规格硬规则过滤（容量/颜色/型号必须一致）

### 5.3 存储层
- PostgreSQL：`products`（商品主档）、`offers`（各平台报价+券明细）、`price_snapshots`（每日快照，append-only）、`watchlist`、`reports`
- Redis：联盟 API 查询结果缓存（TTL 30 分钟）、限流计数

### 5.4 服务与前端
- 后端：FastAPI（异步，天然适配并行平台查询）
- 前端（终态为微信小程序）：
  - 技术栈 **Taro + React**：一套代码编译 Web 与小程序，MVP 期 Web 快速验证（无需备案、迭代最快），M3 编译为小程序上架
  - 小程序交互适配：对话流 + 到手价卡片 + 图片上传（识图入口）
  - 跳转链路：京东走 wx.openBusinessView / 平台小程序跳转，淘宝走小程序跳转，拼多多走 web-view + 业务域名（联盟推广链接的落地方式按平台规则逐个验证）
- 部署（小程序硬性要求）：**国内云服务器 + 域名 ICP 备案 + HTTPS**，并在小程序后台配置服务器域名与业务域名；备案周期 1-3 周，M1 期间即启动，与开发并行
- 降价提醒：小程序订阅消息（一次性订阅，用户授权后推送）
- 可观测：每次查询记录 trace（哪个节点耗时、API 失败率），为面试准备量化数据

### 5.5 识图找同款（P1）· 双路设计
| 平台 | 图搜通道 | 说明 |
|---|---|---|
| 京东 | 京东联盟 imageSearch（jd.union 图搜物料） | 支持直接传 base64，联盟账号 1 万次/日，需申请物料搜索权限 |
| 淘宝 | 拍立淘：阿里云「图像搜索(淘宝联盟版)」或第三方转链服务图搜接口 | 官方 TOP 接口需阿里妈妈开发者资质，个人先走折淘客类通道 |
| 拼多多 | **无官方图搜 API，走 VLM 路线** | 任何声称"拼多多图搜 API"的第三方均为逆向，不碰 |

**VLM 兜底路线（通用，覆盖全部平台）**：
图片 → Qwen-VL 识别（品类/品牌/型号/规格/颜色，结构化输出）→ 组装关键词 → 联盟关键词搜索 → 复用同款匹配管线（embedding + 规格规则）→ 到手价比价。

设计要点：
- 图搜返回的多是"相似款"，必须过同款匹配 + 置信度展示，不假装同款
- VLM 识图与图搜 API 互为校验：两条路结果交叉验证可提升准确率（面试可讲多模态信息融合）
- 识图入口放在对话流中：用户发图即触发，无需切页面

### 5.6 候选消歧与分组策略（图搜 50 个相似商品怎么比）
**四层漏斗**（每层解决一类错误）：
1. **规格硬规则过滤**：型号/容量/颜色/代际 token 必须一致——解决"拿 128G 和 256G 混比"（确定性错误）
2. **向量相似度分档**：商品标题+主图 embedding，阈值分"同款/近似"两档——解决"型号对但不是同款"（语义相似度问题）
3. **价格离群检测**：同款组内用 IQR 剔除异常低价（山寨/瑕疵/临期）——解决"假低价污染比价结果"
4. **LLM 复核**：对 top 候选做结构化对比，生成差异说明；**只做判断和解释，不参与计算**——解决"边界 case 的语义裁决"

**分组呈现**（产品核心决策：分组而非列表）：
- **A 确认同款**（高置信度）：直接进到手价比价，只给最优解
- **B 近似款**（同品牌不同规格/代际/配色）：折叠展示，逐条标注差异（"类似，但为 256G 版本，到手价高 ¥80"）
- **C 可疑低价**：疑似非正品/二手/瑕疵——**参与比价，但强制附加"疑似非正品"警示标签**，视觉上明显区分（置灰+警示色），排序默认置底。原则：平台负责信息透明，不替用户做决定
- **用户筛选开关**：设置中提供"比价范围"选项——默认「排除疑似非正品」，可切换「全部显示（带标注）」；后续版本可扩展更多筛选维度（仅自营/旗舰店、最低店铺评分、包邮）。筛选权交给用户，警示责任留给平台
- **用户反馈回路**：每组均可一键纠错（"这不是同款"），反馈用于调阈值和规则，形成数据飞轮

**面试叙事**：这是"多候选消歧"问题——规则层（确定性）、向量层（语义）、统计层（离群）、LLM 层（裁决）各管一类错误，混合系统设计的典型样板。

## 6. 合规设计（写进简历的加分项）
- 全部数据走官方联盟 API / 授权转链服务，不触碰平台反爬对抗
- 不申请、不存储任何用户电商账号凭据
- 价格数据仅展示"实际观测天数"，不伪造历史
- 报告固定附免责声明 + 数据来源链接（可溯源）

### 6.1 小程序主体与类目策略（终态上架的关键约束）
- **电商-导购类目需要企业/个体工商户主体，个人主体不可申请**；且小程序主体注册后不可升级变更，必须一开始想清楚
- 本品**不含支付、不给用户返利提现**，定位"价格查询工具"：MVP 以个人主体走"工具-查询"类目上架尝试（成本最低）
- 若审核被驳（导购跳转被认定为经营行为）：注册个体工商户（应届生可办、成本低、周期短）重新以经营主体上架；此为预案 B，不阻塞开发
- 联盟佣金归开发者（PID 绑定），不在小程序内做任何"返利/提现"功能，规避金融类目风险

| M3（第 9-10 周） | Taro 编译小程序 + 提审上架（类目策略见 6.1）+ MCP Server 封装 + 简历/面试叙事打磨 | **小程序上线 + 简历定稿** |

## 8. 数据指标
- 北极星：单次查询平均为用户识别的省钱额（到手价差）
- 质量：链接解析成功率 ≥ 95%、同款匹配准确率 ≥ 90%（人工抽检）、报告响应 P90 < 15s
- 留存：查询用户 7 日回访率

## 9. 面试叙事（提前定调）
- **难点 1 数据层**：为什么不能用爬虫 → 反爬成本与合规 → 联盟 API 的配额/缓存设计
- **难点 2 同款匹配**：跨平台 SKU 对齐 = embedding 召回 + 规格规则校验的混合方案，纯 LLM 不可靠
- **难点 3 LLM 边界**：算钱必须确定性（到手价引擎是纯函数），LLM 只做理解与表达——这是"懂工程"的信号
- **协同**：与已有 RAG 问答项目串成"检索增强决策"故事线（多源信息抽取 → 结构化推理 → 可溯源输出）

## 10. 风险与预案
| 风险 | 预案 |
|---|---|
| 联盟 API 审核慢/配额低 | M0 先只做京东，用审核等待期开发引擎与前端 |
| 识图搜到的是相似款而非同款 | 同款匹配硬规则过滤 + 置信度展示；VLM 与图搜 API 双路交叉校验 |
| 小程序类目审核被驳（导购类需经营主体） | 先以个人主体"工具-查询"类目提审；被驳则注册个体工商户转经营主体，不阻塞 M0-M2 开发 |
| 联盟推广链接在小程序内跳转受限 | 逐平台验证跳转链路（小程序跳转/openBusinessView/web-view 业务域名），M1 期间提前踩坑 |
| 淘宝第三方转链服务涨价/失效 | 淘宝降级为"手动粘贴链接解析"，核心叙事不受损 |
| 同款误配（不同容量混比） | 规格硬规则前置过滤 + 置信度展示 + 用户反馈回路 |
| 优惠券规则变化导致到手价算错 | 到手价明细逐项列公式，用户可核对；快照留痕可回溯 |
